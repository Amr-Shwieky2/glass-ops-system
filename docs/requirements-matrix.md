**Implemented:**

## (a) Status vocabulary and evidence rules

| Status | Meaning |
|---|---|
| **IMPLEMENTED** | Requirement fully met: server-enforced, UI-wired, and (where claimed) test-covered. No open sub-gap found by any verifier, refuter, or probe. |
| **PARTIAL** | Core mechanism exists and works for the common path, but a named sub-requirement, edge case, or scope is unmet (e.g., feature works but isn't tested; permission exists but one surface bypasses it). |
| **MISSING** | No code path implements the requirement (schema may exist, but nothing reads/writes it, or no UI/action exists). |
| **SECURITY ISSUE** | A verifier, refuter, or live probe demonstrated (via source trace to a reachable, unauthenticated-or-under-privileged code path, or via live HTTP proof) that unauthorized data is retrievable or an unauthorized mutation is possible. |
| **BROKEN** | Code exists and is reachable but produces incorrect behavior on a realistic path (not a security boundary issue), or a documented setup step fails from a fresh checkout. |
| **SCHEMA ONLY** | Database columns/tables exist for the capability but zero application code path reads or writes them. |
| **DATA INTEGRITY** | (finding-level tag, not a top-level status) — a defect that corrupts stored financial/operational data without necessarily being an authorization bypass. |

**Reconciliation rules applied (per task instructions):**
1. Where a refuter marked `refuted: true` against an IMPLEMENTED domain verdict, the refuter's `newStatus`/`reason` replaces the domain verdict (12 items changed this way; 2 of them are *escalations* to SECURITY ISSUE/BROKEN, not downgrades to PARTIAL).
2. Where two domains rated the same item (only V1/V2, rated MISSING by both `auth-security` and `finance`), the stricter status is kept and evidence merged.
3. Where a live probe finding contradicts or is not yet reflected in a verdict, the probe wins and the item is escalated to SECURITY ISSUE (applied to S1.7, R1.15; corroborating-only probe evidence is folded into existing SECURITY ISSUE items without further escalation).
4. One item (R1.58) was refuted for citing a non-existent evidence file, but this session's own **live E2E run** (29/29 passed, see §f and the Sprint Status doc) independently supersedes that specific concern; R1.58 is reported IMPLEMENTED with the refuter's citation defect noted as a documentation-hygiene caveat, not a functional gap.

## (e) Findings not tied to a single checklist item

### CRITICAL

1. **`completeInstallationAction` has no ownership/involvement check at all, and trusts client-supplied job-item IDs.** `src/server/appointments/complete-installation.ts:38-41` checks only `can(user, COMPLETE_INSTALLATION)` — no `isAppointmentAssignee` check (contrast `markAppointmentArrivedAction`, which does check). Line 98-103 does `UPDATE job_items SET status='installed' WHERE id IN (params.jobItemIds)` with **no `job_id = appointment.jobId` predicate at all**. Line 105-117 calls `recordCustomerPayment` against `appointment.jobId` with **no COLLECT_PAYMENT check**. Any seeded installer (Basel/Issam hold `complete_installation` with only `view_assigned_jobs`) who obtains any appointment UUID can complete an arbitrary appointment on an arbitrary job, mark job items from **any job** installed, advance that job to `installed`, and record a customer payment on a job they are not assigned to. This is the single worst-scoped mutation found in the codebase (worse than the other S1.3 findings because it combines missing job-scope, missing entity-scope, and missing financial-permission checks in one action).

2. **Login has zero rate limiting or lockout — live-demonstrated unlimited credential guessing against a real account.** `src/app/(public)/login/actions.ts:40-98` has no attempt counter, delay, CAPTCHA, or lockout anywhere. **Live Probe 2** sent 25 sequential wrong-password attempts against `+972501111111` (a real, active seeded user) and every one returned HTTP 200 with the identical generic error, at flat bcrypt-only latency (0.23-0.29s), with no 429 at any point; the account was confirmed `status='active'` after the flood. This is the S1.7/R1.48 gap made concrete with live proof against production-shaped data, not a hypothetical.

3. **`approveFactorySubmission`/`rejectFactorySubmission` trust the caller-supplied `jobId` instead of `request.jobId`, with no row lock.** `src/server/production/approve.ts:30-80` never compares the client-supplied `jobId` parameter (bound directly to a client button click, `factory-decision-buttons.tsx:134`) against the submission's real job. The `job_costs` INSERT and `advanceJobStatus` both use the raw parameter. An `APPROVE_FACTORY_PRICE` holder can book a real, approved factory cost — and advance job status — on a job they are not even involved in, simply by tampering with the action's arguments; the real request's own job is left "approved" with no cost row. Confirmed independently by the `auth-security`, `production-factory`, and `finance` domain agents, and this was the specific defect that caused the `production-factory` refuter to downgrade R1.29 from IMPLEMENTED to PARTIAL. No row lock also means two concurrent approvals can double-book the cost.

4. **Customer PII, including national ID, is retrievable by any user holding only `VIEW_CUSTOMERS` — with zero job-involvement scoping, unlike every other entity page in the app.** `src/app/(app)/customers/[id]/page.tsx:33-37` gates on `VIEW_CUSTOMERS` alone; `getCustomerById` (`customers/queries.ts:58-64`) has no ownership predicate at all. **Live Probe 1**, logged in as a real seeded technician (Basel) via the actual login form, opened the customer-detail page for a customer on a job he has zero relationship to and received a full 200 OK profile; a second probe against Ahmad's customer page returned the literal national ID string `300123456` in the page body. Reproduced independently against two more customers as a second low-privilege user (Issam). This is the customer-domain analog of finding #3 above and is the most severe of the several sale-price/PII exposures catalogued throughout this matrix (R1.15, S6.4, I5) because it exposes government-ID-grade PII, not just a price.

5. **Sale price and factory-submitted cost are rendered to every involved job viewer, including installers with zero financial permission — the single most-corroborated finding in this audit.** Independently found and confirmed by 5 of the 9 domain verifiers (auth-security, customers-jobs, production-factory, scheduling, and indirectly finance/dashboard via the reports pathway), tied to formal items R1.10, R1.41, P4, I5, S1.4, S1.5, S6.4, T4, RG13. Root cause is architectural: `ProductionSection` (`jobs/[id]/page.tsx:449-455`) and the job/jobs-list/customer-page sale-price renders are the only sections on the job page with no permission gate at all, while every other financial card (Costs, Compensation, Payments) is correctly gated. A single fix — gating `ProductionSection`'s price/history block on `VIEW_JOB_COSTS` and adding a dedicated sale-price permission everywhere `salePriceTotal` is rendered — would resolve the majority of the SECURITY ISSUE items in this matrix.

### HIGH

1. **`convertQuoteToJob` and `saveQuoteDraft`/`sendQuoteAction` never verify the quote belongs to the job, or that the caller may see the job.** `src/server/quotes/actions.ts:232-288` passes the caller-supplied `(jobId, quoteId)` pair straight to `applySignedQuoteToJob`, which deletes job Y's items and overwrites its sale price/quote pointer/closer with data from an unrelated signed quote X. `saveQuoteDraft`/`sendQuoteAction` have the same gap for creating versions and advancing status on foreign jobs.

2. **`deleteJobItem`, `removeAssignment`, `cancelAppointmentAction` all delete/mutate by row ID alone with no job-match check**, letting a `CREATE_PRICE`/scheduling-permission holder delete items or cancel appointments on jobs they cannot even open (`jobs/actions.ts:341-358,420-437`; `appointments/actions.ts:226-258`). Audit rows record the client-supplied `jobId` in every case, so the audit trail itself is poisoned.

3. **`createMeasurement` lets a restricted user self-escalate to full job visibility.** `jobs/actions.ts:173-181` checks only `CREATE_MEASUREMENT`; line 239-246 unconditionally sets `jobs.measuredByUserId = caller`, and `involvementFilter` treats that column as involvement everywhere (job page, jobs list, attachment route, quote PDF route). A `VIEW_ASSIGNED_JOBS`-only user who learns any job UUID (from a notification href, calendar payload, or shared link) can attach a measurement to it and thereby unlock the full job page, including sale price and factory cost.

4. **`/repairs` and `/customers` list pages leak company-wide data to users scoped to only their own jobs.** `/repairs` (`repairs/page.tsx:50-66`) gates on `CREATE_REPAIR` alone with no `restrictToUserId`; live-reproduced against Basel showing all 6 repairs including 2 jobs his own `/jobs/[id]` page correctly Forbids. `/customers` (`customers/page.tsx:33-40`) has no permission check at all.

5. **Self-approval of financial requests is possible everywhere and is silent** (formal items V1/V2, S1.6): no `decide`/`confirm` action in the codebase checks requester ≠ decider, and several auto-approve paths (`payments/record.ts`, `costs/actions.ts`, `compensation/actions.ts`) skip the approval queue entirely for the requester's own submission. DB shows 4 self-approved payments and 5 self-approved job costs already live in the seed data.

6. **The R1.33 installation-completion note is silently discarded, and the "photo taken" flag is not persisted anywhere queryable.** `complete-installation.ts:105-117` only writes `note` inside the `paymentCollected` branch (as the payment's own notes field) — a technician who completes without collecting payment loses whatever they typed; `photoTaken` exists only inside an `audit_logs` JSON blob, with no column on `appointments`/`jobs` and no display anywhere.

7. **Both `requirements-checklist.md` and `sprint0-checklist.md` (and a prior `coverage-synthesis.md`) referenced by this task's own instructions were not present in the scratchpad for 2 of the 9 domain agents** (`ui-localization-jobdetails`, `tests-deploy-docs-seed`), who had to reconstruct item wording and IDs from the task brief's own hints rather than the source-of-truth checklist text. Statuses/evidence for those ~29 items (R1.9-R1.11, R1.44, R1.45, R1.50, R2.2, S8.1-S8.2, S9.1-S9.3, R1.1-R1.4, R1.46-R1.47, R1.54-R1.58, P6, S10.1-S10.4, RG1-RG6, RG15, D1-D10) are independently well-evidenced from source/live testing, but their exact item-ID mapping against the *original* checklist could not be double-checked. The orchestrating process should confirm these files were actually generated for this sprint before treating this matrix as the final word on IDs.

### MEDIUM

1. **Re-signing a revised quote (v2) wipes and re-creates all `job_items`**, losing installed-status flags and item-linked assignments/costs (`quotes/convert.ts:51-63` unconditionally deletes then re-inserts with status `pending`); the existing factory request is not refreshed, so the factory keeps v1 specs after a v2 signature.
2. **Duplicate-phone customer creation crashes or surfaces raw English Postgres errors** in the office flows (`customers/actions.ts:77-88,132-143`, `jobs/actions.ts:86-99`) — only the field-measurement quick-submit path implements find-or-reuse; no `error.tsx` exists anywhere to catch the resulting unhandled exception gracefully.
3. **`/finance` shows every incoming/outgoing check to any `COLLECT_PAYMENT` holder** (`finance/checks-section.tsx:94-97`), including seeded installers who hold `collect_payment` but not `manage_checks` — company-wide check data (customer names, amounts, banks, payees) reaches a non-financial role.
4. **`cash_expense_reports` (the field-expense-report feature) has zero test coverage and zero seed data** — a fully-wired feature (schema + action + UI) that no automated suite and no demo dataset ever exercises.

8. **Auto-generated factory-request text interpolates a raw English unit key** (`meter`/`unit`) instead of the localized Arabic label the manual path uses, despite a doc comment claiming the two paths are mirrored.

8. **Global search omits address and quote-number**, and the existing btree indexes cannot serve the leading-wildcard `ILIKE '%term%'` queries actually issued (no `pg_trgm`/GIN index anywhere in the migrations).
9. **A stale, untracked git worktree** (`.claude/worktrees/charming-mayer-6a13b7/`) sits in the working tree — harmless (never committed, no real secrets) but dead weight that could confuse a future `git add -A`.
10. **`commission.ts`'s unique-violation recovery reads `err.code` instead of `err.cause.code`**, unlike every other module in the codebase that documents and correctly unwraps Drizzle's error-wrapping — the documented race-recovery path for concurrent commission estimate/finalize almost certainly never triggers.
